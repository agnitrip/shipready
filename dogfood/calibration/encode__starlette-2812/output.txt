+# Fix for Middleware Exception Handling Regression
+
+## Issue Description
+When `BaseHTTPMiddleware` is added to a FastAPI app, exceptions raised in mounted sub-apps that inherit from `Exception` were being silently handled (no traceback in console), while exceptions inheriting from `BaseException` worked correctly.
+
+## Root Cause
+In `/testbed/starlette/middleware/base.py` at line 142, the code was only catching `Exception` but not `BaseException`:
+
+```python
+except Exception as exc:
+    app_exc = exc
+```
+
+This meant:
+1. **Exception subclasses**: Got caught and stored in `app_exc` but the re-raise mechanism failed
+2. **BaseException subclasses**: Bypassed the catch and propagated normally to the server for logging
+
+## The Fix
+Changed line 142 in `/testbed/starlette/middleware/base.py` from:
+```python
+except Exception as exc:
+```
+to:
+```python
+except BaseException as exc:
+```
+
+## Why This Fix is Correct
+
+1. **Addresses the Regression**: Fixes the issue described in #2625 which was a regression of #1976, #1977, #1609, #1940
+
+2. **Maintains Proper Exception Flow**: The exception is still stored in `app_exc` and re-raised later at lines 154 and 169, ensuring it reaches the server for logging
+
+3. **Consistent with Starlette's Design**: Other Starlette middleware like `ServerErrorMiddleware` also catch `Exception` but re-raise it, following a similar pattern
+
+4. **Minimal Risk**: While catching `BaseException` can be risky in general, in this specific context:
+   - The exception is immediately re-raised later in the code
+   - It only affects the middleware's internal exception handling
+   - It doesn't mask critical exceptions like KeyboardInterrupt for long
+
+## Verification
+
+### Before the Fix:
+- `/info` (main app): ✅ Shows exception traceback
+- `/private/info` (mounted app): ❌ Silent failure (no traceback)
+
+### After the Fix:
+- `/info` (main app): ✅ Shows exception traceback  
+- `/private/info` (mounted app): ✅ Shows exception traceback
+
+## Test Case
+Use the provided `/testbed/reproduce_issue.py` to verify:
+1. Run `python /testbed/reproduce_issue.py`
+2. Make requests to both endpoints
+3. Verify both show the same exception traceback in the console
+
+## Files Modified
+- `/testbed/starlette/middleware/base.py`: Line 142 (single character change: `Exception` → `BaseException`)
+
+## Impact
+- **Breaking Changes**: None - this fixes a regression, restoring previous behavior
+- **Performance**: Negligible - exception handling overhead is minimal
+- **Security**: No impact - this only affects how exceptions are logged, not how they're processed

+# Issue Analysis: Middleware Causes Exceptions to Be Handled Silently (Regression)
+
+## 1. Core Issue Information
+
+### Issue Type
+Bug Report - Regression of previously fixed exception handling behavior
+
+### Problem Statement & Symptoms
+When Starlette's `BaseHTTPMiddleware` is added to a FastAPI application:
+- Exceptions raised in the **main application** routes show tracebacks in stdout (correct behavior)
+- Exceptions raised in **mounted sub-application** routes are handled silently (no traceback in stdout, incorrect behavior)
+
+Key observation: Changing exception inheritance from `Exception` to `BaseException` makes all exceptions show tracebacks.
+
+### Expected vs Actual Behavior
+| Scenario | Expected Behavior | Actual Behavior |
+|----------|-------------------|-----------------|
+| Main app route with middleware | Exception traceback in stdout | ✅ Traceback shown |

+| Any route without middleware | Exception traceback in stdout | ✅ Traceback shown for all |
+
+### Affected Components

+- FastAPI application mounting (`app.mount()`)
+- FastAPI exception handling system
